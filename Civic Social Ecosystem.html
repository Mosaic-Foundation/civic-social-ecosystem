Ecosystem Overview

Civic.Social

Open, federated infrastructure for civic participation — the connective layer that lets independent civic tools, governments, and organizations interoperate. A Civic Hub is a community-scoped civic space; a Citizen Dashboard is an individual-scoped civic space. Both are applications that read the protocol and host processes appropriate to their scope.

Civic Hubserver-side · federated

A community's civic space — rendering software operating on the Community Node and Community Data Store the community itself owns. Change hubs, keep the community. Operators add democratic-process plugins (votes, deliberation, proposals, town halls), and admin console, AI assistants, and pipelines for ingesting external civic data (meeting minutes, voting records, public records) are part of every hub, not separate products.

Reusable building blocks — one engine, many lenses
scope ▸ ecosystem-wide
component · core

Activity Feed

A single activity engine. Five lenses produce different feeds from the same substrate — one activity can surface in several at once.

InboxAggregated activity from things you follow. Hubs, processes, profiles you've subscribed to, ranked by recency. Browse mode — no read state.
NotificationsActivities directed at you specifically. @-mentions, votes you're eligible for, credentials issued to you, deadlines. Read/unread state — attention mode.
DiscoveryUnsubscribed activity. Find new hubs, processes, and issuers worth following.
Hub ViewPer-hub activity slice. Everything happening inside a single hub.
EmbedFiltered activity surface a third-party site can drop into any page.
shippable as embed
component · runtime

Processes

Modular interactive process units — votes, proposals, deliberation — plus the runtime that hosts them. Each process can also stand alone as its own interface: a single vote, deliberation, or proposal lives at its own URL, independent of any hub or dashboard.

shippable as embed
component · citizen

Citizen Console

Renders the Citizen Node — DIDs, credentials, and capabilities held by the person. The user-facing surface for "who I am."

component · citizen

PDS

Renders the Personal Data Store — social graph, subscriptions, preferences. The user-facing surface for "what I follow and care about."

component · embedded

Identity Adapter

Reads DIDs, verifies credentials. Sits inside every interface.

component · embedded

Access Control

Checks who can do what. Role-based near-term; capability-based long-term — built as a swappable layer so the policy engine can evolve without rewriting interfaces. Sits inside every interface.

✦ Shippable as embed — these two components also work as standalone widgets a third party can drop into any web page. A city portal can host an Activity Feed · activity stream; a news site can host a Processes · vote widget — no rest-of-the-stack required.

Entity NodeDID + credentials for any public role

Identity for any public-role participant — representatives, candidates, issuers, institutions. Anchors the entity's public surface and what it's authorized to do.

entity · data

Entity Data Storerole-owned content

Whatever the role owns — issued credentials, official statements, response history, badges. Belongs to the role, not to any platform that displays it.

community · identity

Community Nodecollective DID + credentials

The community's collective identity — its DID and the credentials of its officers or members. Persists across hub software; the community is not the hub.

community · data

Community Data Storemember-owned content

Member roster, posts, decisions, ingested civic data, moderation history. Belongs to the community — change hub vendors, keep everything.
